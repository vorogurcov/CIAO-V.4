# Техническое задание: доработка рантайма CIAO

## 1. Основание

ТЗ подготовлено по результатам сравнения текущей реализации с `ImplementationOfCIAO.docx` и фиксирует обязательные доработки:

- обеспечить корректную event-driven модель исполнения через очередь событий;
- обеспечить параллельный запуск автоматов на уровне планировщика исполнения;
- убрать ограничение на только двусвязные (бинарные) отношения в модели связей.

## 2. Цель работ

Реализовать новый runtime интерпретатора CIAO, в котором:

1. события обрабатываются через явную очередь и диспетчер;
2. автоматы исполняются кооперативно и параллельно (по независимым событиям/объектам);
3. связи поддерживают маршрутизацию не только 1:1, но и 1:N / N:1 / N:N в рамках формализованной модели.

## 3. Границы работ

### В рамках ТЗ

- рефакторинг интерпретатора (`interpretator/`);
- новая модель очереди и диспетчера;
- обновление модели links и парсинга;
- обновление тестовых сценариев и документации.

### Вне рамок ТЗ

- изменение синтаксиса CIAO без необходимости;
- оптимизация компилятора `compiler/`, если не требуется для runtime;
- UI/IDE-интеграция.

## 4. Термины

- **Event**: адресованное событие с именем, аргументами, метаданными.
- **Dispatcher**: цикл, извлекающий события из очереди и передающий в обработчик.
- **Handler**: логика выполнения одного шага автомата по событию.
- **Storage**: доступ к внутреннему представлению объектов/состояний.
- **Link**: правило маршрутизации от интерфейса-источника к одному или нескольким интерфейсам-получателям.

## 5. Текущее состояние (as-is)

- основной поток исполнения: рекурсивные вызовы `interpret()` из `interpretActions()`;
- очередь событий как отдельный компонент отсутствует;
- отдельный поток есть только для `after(...)`;
- links фактически реализованы как бинарные пары (`source -> target`).

## 6. Целевое состояние (to-be)

### 6.1 Архитектура runtime

Обязательные компоненты:

1. `EventQueue`  
   Потокобезопасная очередь событий (`put`, `get`, `is_ready`, `shutdown`).

2. `Dispatcher`  
   Главный цикл обработки: извлечение события, передача в `Handler`, постановка новых событий в очередь.

3. `Handler`  
   Выполнение шага автомата:
   - выбор перехода по `(object, event, state)`;
   - проверка условий;
   - смена состояния;
   - выполнение эффектов;
   - генерация новых событий (через очередь, без рекурсии).

4. `StorageAdapter`  
   Доступ к объектам, состояниям, интерфейсам, links.

### 6.2 Параллелизм

Обязательная модель:

- `Dispatcher` + пул воркеров (или эквивалентная модель), где:
  - события разных объектов могут исполняться параллельно;
  - для одного объекта соблюдается последовательность обработки событий;
  - присутствует механизм синхронизации на уровне объекта (lock/actor-mailbox).

Ограничения:

- недопустима бесконтрольная рекурсия событийных вызовов;
- `after(...)` должен генерировать событие в очередь, а не напрямую менять состояние.

### 6.3 Модель связей (links)

Требования разделяются на две части:

1) **Внешняя форма программы (`scheme.links`) остаётся бинарной**: каждая запись связывает требуемый интерфейс (required) с одним предоставленным интерфейсом (provided) как задано метамоделью (`Interface.link : { a, p }`).

2) **В runtime должна поддерживаться маршрутизация с fan-out (1:N)** через **внутреннюю нормализацию/агрегацию** нескольких бинарных `links`-записей с одним и тем же `source` (и/или применение заданной `policy`).

Целевая семантика маршрутизации:

- 1:1 (обратная совместимость);
- 1:N (один источник, несколько получателей) как результат нормализации по набору бинарных `links`;
- N:1;
- N:N через набор правил.

Минимальная целевая структура **внутреннего** link-правила (post-normalization):

```text
{
  "source": "objA.effectX",
  "targets": ["objB.eventY", "objC.eventZ"],
  "policy": "broadcast|first|all",
  "filter": null
}
```

Требования:

- существующий бинарный формат `scheme.links` должен автоматически преобразовываться во внутреннюю структуру с `targets`;
- маршрутизация выполняется только через очередь событий.

### 6.4 Event-driven семантика

Обязательные правила:

- любое действие `call` создаёт `Event` и ставит его в очередь;
- порядок обработки внутри одного объекта детерминирован;
- межобъектный порядок фиксируется политикой диспетчера и логируется;
- поддерживается tick-driven последовательность там, где требуется по модели CIAO v.3.

## 7. Функциональные требования

### FR-1 Очередь событий
- Реализовать `initQ`, `putQ`, `getQ`, `moveQ/isReadyQ` в виде runtime API.

### FR-2 Диспетчер
- Реализовать цикл обработки до опустошения очереди/команды завершения.

### FR-3 Обработчик переходов
- Выполнять один переход на событие согласно таблице состояний.

### FR-4 Эффекты и генерация событий
- Эффекты, вызывающие интерфейсы, не должны напрямую вызывать `interpret`.

### FR-5 Параллельный запуск
- Поддержать конкурентную обработку событий для разных объектов.

### FR-6 Расширенные links
- Поддержать множественные цели в связи.

### FR-7 Таймеры
- `after` публикует событие в очередь; отмена/перезапуск корректно синхронизированы.

### FR-8 Трассировка
- Логировать `event_id`, `source`, `target`, `timestamp`, `worker_id`, `result_state`.

## 8. Нефункциональные требования

### NFR-1 Надёжность
- Отсутствие переполнения стека на длинных цепочках событий.

### NFR-2 Потокобезопасность
- Отсутствие race condition при одновременной обработке нескольких объектов.

### NFR-3 Производительность
- При 1000 событий в очереди система не деградирует критически (целевой KPI уточняется на этапе реализации).

### NFR-4 Наблюдаемость
- Должны быть включаемые диагностические логи маршрутизации и исполнения.

## 9. Требования к обратной совместимости

1. Существующие программы CIAO с бинарными links должны исполняться без изменения исходников.
2. Старая запись links допускается, но интерпретатор переводит её во внутренний расширенный формат.
3. Публичные команды интерактивного режима сохраняются (`help`, `interfaces`, `exitCode`).

## 10. Изменяемые модули

- `interpretator/interpreter.py` — декомпозиция и переход на queue-based runtime;
- `interpretator/createTable.py` — расширение `parse_links` и нормализация links;
- `reservFunc/after.py` — интеграция с очередью событий;
- `docs/03-INTERPRETATION.md` — актуализация описания исполнения;
- при необходимости: новые файлы `interpretator/runtime/*.py`.

## 11. План реализации (этапы)

### Этап 1. Каркас runtime
- Ввести `Event`, `EventQueue`, `Dispatcher`, `Handler`, `StorageAdapter`.

### Этап 2. Перенос логики переходов
- Перенести логику из текущего `interpret()` в `Handler.process_event()`.

### Этап 3. Устранение рекурсии
- Все вызовы по links заменить на `queue.put(event)`.

### Этап 4. Параллельный планировщик
- Добавить worker pool + сериализацию событий на объект.

### Этап 5. Расширение links
- Реализовать новую модель links и обратную совместимость.

### Этап 6. Таймеры
- Перевести `after` на публикацию событий в очередь.

### Этап 7. Тесты и документация
- Добавить unit/integration сценарии и обновить документацию.

## 12. Критерии приёмки

### AC-1 Очередная модель
- В runtime отсутствуют рекурсивные вызовы обработки событий между объектами.

### AC-2 Параллельность
- События разных объектов могут обрабатываться одновременно.

### AC-3 Последовательность объекта
- Для одного объекта соблюдается корректный порядок переходов.

### AC-4 Links
- Поддерживаются 1:N связи и подтверждаются тестами.

### AC-5 Таймеры
- `after` не нарушает модель очереди и корректно отменяется.

### AC-6 Регрессия
- Базовые примеры из `TestPrograms/` продолжают работать.

## 13. Минимальный набор тестов

1. **QueueFlow**: цепочка из 100+ событий без переполнения стека.  
2. **ParallelObjects**: два независимых автомата обрабатывают события параллельно.  
3. **SingleObjectOrder**: серия событий одного объекта не нарушает порядок.  
4. **LinksBroadcast**: один source отправляет событие двум targets.  
5. **AfterEnqueue**: таймер публикует событие в очередь и корректно отменяется.  
6. **CompatibilityBinaryLinks**: старый формат links исполняется без изменений.

## 14. Риски и меры

- **Риск**: race condition при параллельной обработке.  
  **Мера**: изоляция обработки по `object_id`, блокировки/почтовые ящики.

- **Риск**: изменение порядка событий может сломать существующие сценарии.  
  **Мера**: режим совместимости + детальная трассировка.

- **Риск**: усложнение отладки.  
  **Мера**: структурированные логи и тесты на воспроизводимость.

## 15. Результат работ

Итогом является обновлённый интерпретатор CIAO с queue-based runtime, поддержкой параллельного исполнения автоматов и расширенной моделью связей, подтверждённый тестами и документацией.
