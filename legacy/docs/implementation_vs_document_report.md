# Сравнение текущей реализации CIAO с `ImplementationOfCIAO.docx`

## Цель

Сопоставить фактическую реализацию в репозитории с описанной в документе архитектурой и семантикой исполнения, с приоритетом:

1. Параллельный запуск автоматов.
2. Поддержка отношений между автоматами (текущее ограничение до двусвязного/бинарного случая).

## Что взято за эталон из документа

По тексту документа (Listing 1/2/3/4/5, Table 1, Fig. 1, Fig. 2) ожидается:

- внутреннее представление через структуры `CIAO_Prog`, `Auto_Obj`, `Event`;
- событийная модель через очередь (`initQ`, `putQ`, `moveQ`, `getQ`);
- обработка события как отдельный шаг интерпретации с постановкой новых событий в очередь;
- декомпозиция интерпретатора как минимум на роли `Dispatcher`, `Queue`, `Handler`, `Storage`;
- строгая event-driven модель (в CIAO v.3 последовательность эмулируется через `tick`, а не спонтанные переходы);
- взаимодействие автоматных объектов через схему связей интерфейсов.

## Что реализовано фактически

Ключевые точки реализации:

- `interpretator/interpreter.py`
- `interpretator/createTable.py`
- `reservFunc/after.py`
- косвенно: `compiler/output.py`, `interpreterBootstrap.py`

### Наблюдаемая модель исполнения

- В `interpretator/interpreter.py` исполнение инициируется вызовом `interpret(interface, isUser)`.
- Из `interpretActions()` при вызове эффекта по связи выполняется непосредственный рекурсивный вызов `self.interpret(event_link, False)`.
- Это даёт глубинный (call-stack) обход цепочки вызовов, а не явную очередь событий.
- Отдельный поток используется только для `after(...)` через `TimerManager` (`threading.Thread`).

## Ключевые расхождения (с приоритетами)

## P0 (критично)

### 1) Нет полноценного параллельного запуска автоматов

Ожидание по документу: кооперативная обработка событий системой взаимодействующих автоматов с диспетчеризацией (через очередь/циклический обработчик).

Факт:

- параллельность есть только в механизме таймера `after(...)`;
- основные переходы/эффекты выполняются последовательно в одном потоке;
- вызовы по связям синхронны и рекурсивны.

Следствие:

- нет реального конкурентного исполнения автоматов;
- порядок определяется стеком вызовов, что отличается от очередной event-loop семантики.

### 2) Архитектура интерпретатора не соответствует целевой декомпозиции Dispatcher/Queue/Handler/Storage

Ожидание: разделение ролей, где события проходят через очередь, а обработчик шага интерпретации отделён от хранилища.

Факт:

- основная логика концентрирована в одном классе `Interpreter`;
- выделенного runtime-компонента очереди событий нет;
- отдельные роли не оформлены как независимые объекты в основном интерпретаторе.

Следствие:

- труднее обеспечить масштабируемую кооперативность и управляемый scheduling;
- сложнее контролировать fairness и наблюдаемость исполнения.

## P1 (важно)

### 3) Вместо очереди событий используется рекурсивная диспетчеризация

Ожидание: `putQ/getQ/moveQ` и цикл обработки.

Факт:

- событие по связи запускается сразу (`self.interpret(...)`) из контекста текущего действия;
- при длинных/циклических цепочках используется искусственный лимит глубины (`maxDepth`), что косвенно подтверждает стековую модель.

Следствие:

- поведение может отличаться от ожидаемого FIFO-процесса;
- возможны трудноотлаживаемые эффекты порядка исполнения.

### 4) Ограничение на двусвязные (бинарные) связи подтверждено

Ожидание по задаче: важно явно проверить, что текущая реализация действительно ограничена двусвязными отношениями.

Факт:

- парсинг links в `parse_links(...)` формирует ровно одну пару `{source: target}`;
- валидация и исполнение связи работают со строками вида `объект.интерфейс`;
- в рантайме выбирается один `event_link` и выполняется прямой вызов.

Следствие:

- модель связи в runtime фактически бинарная (источник-цель);
- n-арные/многоканальные связи или явная маршрутизация множества получателей не поддержаны как самостоятельная семантика.

## P2 (умеренно)

### 5) Частичное несовпадение с event-driven паттерном через `tick`

Ожидание из статьи: последовательность в CIAO v.3 эмулируется через специальный `tick`.

Факт:

- в основном интерпретаторе универсального механизма `tick`-диспетчеризации нет;
- есть поддержка зарезервированных функций (включая `after`), но не прослеживается общий шаблон event-loop из Listing 5.

## Вывод по ключевому требованию

Текущая реализация подтверждённо:

- **не реализует полноценный параллельный запуск автоматов** (кроме таймера `after` в отдельном потоке),
- **работает в бинарной (двусвязной) модели связей** на уровне парсинга и исполнения.

Следовательно, в текущем виде она не соответствует целевой модели кооперативного взаимодействия автоматных объектов из документа в части runtime-диспетчеризации и многoобъектной координации исполнения.

## Рекомендуемые направления доработки

1. Ввести явную очередь событий (`EventQueue`) и цикл диспетчера.
2. Отделить роли `Dispatcher`, `Queue`, `Handler`, `Storage` в runtime-архитектуре.
3. Заменить рекурсивную передачу событий по links на постановку событий в очередь.
4. Зафиксировать формальную семантику links: если нужна поддержка не только бинарной модели, расширить представление связи и правила маршрутизации.
5. Добавить трассировку порядка обработки событий (идентификаторы событий, timestamp, источник), чтобы валидировать соответствие документной семантике.
